// 03 · how it works

Three rules that keep your users safe, and you out of trouble.

If you remember three things about Andromeda, remember these. They make custody-free real, not marketing.

protocol · i

Two shares. One signature. Neither side wins alone.

A wallet’s signing key is split: one share on your client, one in the MPC network. Producing a signature requires both at the same time.

Compromise one side completely, and no signature ever comes out. Every Wallet you create uses this same split, across every chain.

  • 2PC-MPC threshold signing under the hood
  • Presigns for sub-second approvals
  • Sharded network state
protocol · ii

We never see the user’s key.

Every signing endpoint uses prepare → submit. We return an unsigned payload, your client signs locally with whatever key the user already has, you submit. The service has no path to extract the user’s key.

The pattern is enforced at the API itself, not as a configuration you can flip.

  • POST /v1/sign/prepare → unsigned payload
  • Client signs locally
  • POST /v1/sign/submit → tx hash
protocol · iii

If we disappear, your users keep their wallets.

Wallet state lives on-chain. That’s the source of truth. Our database is just a cache. Wipe it and signing rebuilds from chain. Replace our backend tomorrow and the same user signs in with the same wallet.

Your users own their continuity. A regenerated dWallet would be a different wallet with a different address. We never do that.

  • Canonical on-chain state
  • Cache is rebuildable, never authoritative
  • Cross-client recovery via deterministic addresses
code · the whole thing

From zero to signed in eight lines.

One challenge, one submit, and a signature is produced on-chain. No SDK, no funding required from your user.

# 1. Get a recovery challenge (server returns a canonical message)
curl -X POST https://api.andromedainfra.pro/v1/recovery/challenge \
  -H "X-Api-Key: $ANDROMEDA_KEY" -H "Content-Type: application/json" \
  -d '{"appId":"demo","scheme":"secp256k1-eip191","walletAddress":"0xAbC..."}'

# 2. User signs the message with their wallet → submit
curl -X POST https://api.andromedainfra.pro/v1/recovery/primary/submit \
  -H "X-Api-Key: $ANDROMEDA_KEY" -H "Content-Type: application/json" \
  -d '{"dwalletAddress":"...","messageHashHex":"...","signatureBase64":"...","expectedNonce":7}'
// Plain fetch, no SDK required.
const headers = {
  "X-Api-Key": process.env.ANDROMEDA_KEY,

// 04 · what we promise

Security isn’t a setting. It’s how the platform is built.

We don’t ask you to trust us. We architect things so you don’t have to. Custody-free signing, on-chain policy enforcement, isolated engines, and redacted logs come with the system, not features you opt into.

Our gateway absorbs every public request and applies auth and quotas. Behind it, the signing and FHE engines have no path to the public internet. User signing keys are split via 2PC-MPC and never reconstructed. PII and key material are redacted at source.

  • key custody None. We can’t sign on your users’ behalf. The math doesn’t allow it.
  • recovery On-chain. Wipe our database, your users still own their wallets.
  • private state FHE-evaluated. Sensitive inputs stay encrypted end-to-end.
  • gas fees Abstracted. Users sign with any wallet, never hold native tokens.
  • network exposure Zero. Engines never face the public internet.
  • log discipline Key material never logged. PII redacted at source.
